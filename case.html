One CVE, from crash to proof

Why this CVE. It is small, deterministic, and lives in a library that ships inside countless products (Debian, Fedora, Siemens devices, and everything vendoring expat). The trigger is a 2 KB XML string, so the whole experiment runs in seconds — which is exactly what a demo needs.

The vulnerability

What goes wrong, in one paragraph

An XML document declares an internal entity whose replacement text contains a comment:

<!DOCTYPE a [<!ENTITY e '<!--COMMENT-->a'>]>
<a>&e;<b> …a very long tag name… /></b></a>

The application installs a comment handler and suspends the parser from inside it (XML_StopParser), then resumes later — a normal pattern for streaming parsers that need to hand control back to the caller.

On resume, internalEntityProcessor in xmlparse.c calls doContent() and returns its result without first copying the tag names out of the entity text buffer (storeRawNames). That buffer has already been released during the suspend, so the parser later walks over freed memory. That is the use-after-free.

Step 1

The crash

Built against libexpat 2.4.8, compiled with a guard-page allocator (see the honesty note below), and run:

$ ./ap_vuln.exe
input bytes: 2115, first chunk: 54
step 1 parse(first chunk) -> SUSPENDED
step 2 resume -> OK
[process exit code: -1073741819]
0xC0000005 — access violation

The fault happens on the third step: the parser is asked to continue with the remainder of the document, reaches into the entity text it no longer owns, and dies. Note what is not printed — the process never reached step 3.

Step 2

The patch

The upstream fix is four lines: after doContent returns successfully, store the raw names before returning. That is all it takes to keep the buffer alive long enough.

@@ -5826,10 +5826,15 @@ internalEntityProcessor(...)
   {
     parser->m_processor = contentProcessor;
     /* see externalEntityContentProcessor vs contentProcessor */
-    return doContent(parser, parser->m_parentParser ? 1 : 0, parser->m_encoding,
-                     s, end, nextPtr,
-                     (XML_Bool)! parser->m_parsingStatus.finalBuffer,
-                     XML_ACCOUNT_DIRECT);
+    result = doContent(parser, parser->m_parentParser ? 1 : 0,
+                       parser->m_encoding, s, end, nextPtr,
+                       (XML_Bool)! parser->m_parsingStatus.finalBuffer,
+                       XML_ACCOUNT_DIRECT);
+    if (result == XML_ERROR_NONE) {
+      if (! storeRawNames(parser))
+        return XML_ERROR_NO_MEMORY;
+    }
+    return result;
   }
 }

Step 3

The proof

Three builds, one input, same harness:

This is the whole point of the paper. The patch is not accepted because it looks right, or because a model produced it. It is accepted because the crash that existed before it no longer exists after it — and the fixed release behaves identically.

Where this sits in the pipeline

Honesty note. The patch shown is the upstream fix, used as the reference for what a correct repair looks like. The language-model generator was not run here: this machine has no GPU, and inventing a transcript would defeat the purpose. What is real is everything that usually gets hand-waved — the vulnerable source, the trigger, the fault, the repair, and the before/after evidence. The generator becomes a measured component in the full study (RQ1, RQ2); the gate is what this page proves works.

Limits

What this case does not prove

  • It does not show the generator working — that is a separate experiment with a GPU and a benchmark.
  • It is one CVE, chosen because it is reproducible; it says nothing about the average success rate.
  • The guard allocator is stricter than production: it turns a silent corruption into a fault. That is what makes it useful as an oracle, but it also means "no fault here" is not a guarantee of correctness — which is why the full pipeline also runs regression tests.
  • Source-level fixes only; no live patching, no binary rewriting.

What it does prove is narrower and more useful: the validation gate can distinguish a broken build from a fixed one on a real vulnerability, with evidence a reviewer can rerun.
