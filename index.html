What this shows

An automated patching pipeline for CVE-classified vulnerabilities — and why the ordering decision matters.

The problem

Vendors keep shortening the patch window. Yet most organisations still rank vulnerabilities and hand the list to a human. Prioritisation research stops at the list; repair research fixes whatever it is given. Nothing measures how many validated patches can be shipped end-to-end.

The five stages you are watching

1 · IngestNVD data: CVE, CVSS, CWE, affected versions, exploit likelihood.
2 · PrioritiseOrder by expected value: severity × exploit likelihood × patchability, per unit of review budget.
3 · GenerateAn LLM proposes candidate patches for the selected function.
4 · ValidateCompile, replay the exploit, run regression tests. Only a pass is accepted.
5 · ShipA pull request with proof attached: diff, before/after exploit, test log.

Why ordering matters

Automated generation is cheap; validation is not. A hard memory-corruption bug can consume the same review budget as an easy injection flaw and still fail. Ordering by severity alone therefore wastes budget on vulnerabilities the pipeline cannot fix — which is what the red failures in the scene represent.

What is measured

  • Validated Patch Rate — passes compile, exploit replay and tests.
  • Validated patches per review-hour — the headline number.
  • Critical coverage — share of CVSS ≥ 9.0 fixed within a window.

Scope, stated honestly

In scope: open-source C/C++ with a reproducible proof-of-concept and a function-local repair. Out of scope: authentication and design flaws, race conditions, kernel and closed-source targets, and anything without a reproducible trigger.

Where a vendor already shipped a fix, upgrading is the correct action — this pipeline targets the cases where no adequate fix exists in the deployed version.
