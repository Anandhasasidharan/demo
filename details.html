Technical detail

How a CVE becomes a proven patch

The demo on the previous page is an abstraction. This page is the mechanism: what each stage computes, what can go wrong, what is measured, and what the work deliberately does not cover.

Section 1

The problem is no longer finding vulnerabilities

Organisations do not lack vulnerability data. A scanner produces hundreds of findings per week. What they lack is the capacity to turn findings into shipped, verified fixes. Vendors keep compressing the window in which a fix is expected:

  • Ubuntu Livepatch applies critical kernel fixes without a reboot; Arm64 support arrives with 26.04 LTS.
  • Windows Autopatch enables hotpatching by default in 2026 — monthly security fixes without a restart.
  • Chrome moved from a four-week to a two-week major cycle, with weekly security releases; its patch gap fell from roughly 35 days to about 15.

When the expected turnaround is days, a monthly human triage-and-patch cycle cannot keep up. Automation is not a convenience; it is the only way to fit inside the window.

Section 2

Two literatures that never meet

Prioritisation

Decides what to fix — then stops

Deep VULMAN (2023) uses deep reinforcement learning plus an integer program to choose which CVEs to mitigate and how much staff time to allocate. Its output is a ranked list for humans. No patch is generated, validated, or deployed.

Repair

Writes fixes — for whatever it is given

AIBugHunter (2024) and code-language-model work (2025) generate candidate fixes for vulnerable functions. The input is taken as given: there is no organisational queue, no exploitability context, no deployment step.

The consequence, stated by recent reviews: the end-to-end lifecycle is an open problem. Nothing measures the operational question — how many validated patches per unit of review capacity.

Section 3

The pipeline

The feedback edge is the part the base framework does not have: what happened inside validation changes what is worth doing next.

Section 4

Stage by stage

Stage 1 · Ingest

Turn a CVE identifier into a decision record

Input: CVE ID, plus the asset it was found on.
Output: vuln.json.

# joined record used by every later stage
{
  "cve": "CVE-2026-XXXXX",
  "cvss": 9.2, "cwe": "CWE-787",
  "epss_asof": { "date": "2026-10-20", "p": 0.41 },
  "kev": false,
  "asset": { "criticality": 0.8, "exposure": 0.9, "ids": true },
  "fix_commit": "abc123", "poc": "poc-01"
}

Failure modes: missing CVSS (use the v3.1 base vector if v4 is absent); EPSS queried at the wrong date (this silently leaks the future — see threats); duplicate CVEs across hosts (deduplicate by CVE and merge asset context).

Feeds: every downstream stage. If this record is wrong, everything after it is wrong.

Stage 2 · Prioritise

Decide what is worth attempting this week

Input: the queue of records, a budget, and a patchability estimate.
Output: an ordered queue.

The objective is not "maximise severity covered". It is "maximise validated patches per unit of review capacity". A critical bug that the pipeline cannot fix consumes the same budget as an easy one and returns nothing.

Failure mode: if patchability is over-weighted, the queue drifts toward trivial bugs and critical coverage collapses. The weight is learned and ablated, never assumed.

Stage 3 · Generate

Produce candidate diffs for the localised function

Input: vulnerable function, its CWE, retrieved exemplars, build context.
Output: k unified diffs.

# prompt skeleton
system: You repair C/C++ security vulnerabilities. Return only a unified diff.
user:
  CWE: {cwe_id} — {cwe_name}
  Vulnerable function:
  {function_source}
  Similar fixes for this weakness class:
  {retrieved_examples}
  Constraints: minimal change; no new dependencies; keep the API stable.

Why retrieval: exemplars of the same weakness class raise the probability of a compilable, idiomatic fix far more cheaply than a larger model.

Failure modes: the model edits the wrong region, changes the API, adds a dependency, or "fixes" by removing functionality. All four are caught downstream — that is the point of the gate.

Stage 4 · Validate

Prove the patch, or discard it

This is the contribution. Details in the next section.

Stage 5 · Ship

Hand over evidence, not a suggestion

Output: a pull request containing the diff, PoC output before and after, the sanitizer log, the regression report, and the exact model revision used.

Deployment is a reviewable PR. Automatic merge is deliberately out of scope: a wrong security patch can be worse than the vulnerability.

Section 5

The validation gate

Checks are ordered cheapest-first so that weak candidates die before expensive ones run.

#CheckImplementationOn failure
1Appliesgit apply --check in a clean worktreetry next candidate
2Compilesproject build system inside the benchmark containertry next candidate
3Sanitizesrebuild with -fsanitize=address,undefinedtry next candidate
4PoC silentreplay the original reproducer 3×try next candidate
5Regressionproject test suite (or benchmark harness)try next candidate
6Not a cheatbody deleted, input hardcoded, error swallowed, tests modifiedtry next candidate
7Staticclang-tidy + semgrep on changed lineswarn or reject
The oracle problem. A validation gate is only as good as its reproducer. Datasets without PoCs and tests cannot support claims of correctness — which is exactly why this work uses reproducible benchmarks (ARVO, Sec-bench) and treats "no PoC" as out of scope rather than as a success.
PoC-only validation overestimates correctness. A patch can silence the crash while breaking the program or special-casing the input. The cheat checks and regression step exist to catch that, and the overfit rate is reported rather than hidden.

Section 6

Scoring and ranking

Every attempt spends scarce review capacity, so the correct ordering is by expected value per unit of that capacity:

EV(c) = P(exploit | c) × impact(c) × P(patch validates | c) ÷ cost(c) P(exploit) comes from EPSS, overridden by KEV. impact combines CVSS with asset criticality. The patchability term is the new one: nothing in CVSS, EPSS, KEV or SSVC models whether a fix can actually be produced.

The operational form is a weighted score; the weights are learned on validation episodes and ablated term by term:

priority = w₁·CVSS + w₂·EPSS + w₃·KEV + w₄·asset + w₅·patchability − λ·effort
SignalSourceQuestion it answers
CVSS v3.1 / v4.0FIRSThow bad if exploited
EPSSFIRSTprobability of exploitation in 30 days
KEVCISAis it already being exploited
CWEMITREwhich repair strategy applies
SSVCCISA / SEIdecision-tree baseline
patchabilitythis workcan the pipeline fix it at all
Worked example. Two CVEs, one review-hour each. A: CVSS 9.8, EPSS 0.02, patchability 0.15 → expected validated fixes ≈ 0.003. B: CVSS 8.1, EPSS 0.35, patchability 0.80 → ≈ 0.28. Ranking by severity picks A; expected value picks B, roughly ninety times better per hour.

Overfit ratepasses PoC but rejected by cheat checksexposes patches that game the oracle

Statistics: at least three seeds and thirty episodes per configuration, paired comparisons with the Wilcoxon signed-rank test, medians with interquartile ranges, effect sizes reported.

Section 9

Scope, stated before anyone asks

In scope IN

  • Open-source C/C++, buildable in a container
  • Reproducible crash or PoC
  • Function-local repair (≤ ~50 lines, ≤ 2 files)
  • Memory safety: CWE-787, 125, 416, 476, 190
  • Injection: CWE-89, 78, 79, 22

Out of scope OUT

  • Authentication and design flaws (CWE-287, 306)
  • Race conditions, crypto misuse, side channels
  • Kernel, firmware, closed source, binaries
  • Multi-file redesigns
  • Anything without a reproducible trigger

Where a vendor fix exists, upgrading is the correct answer and this pipeline says so instead of hand-patching. It targets the gap: no adequate fix in the deployed version, or a required backport.
